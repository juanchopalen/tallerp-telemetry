# Protocolo GT02 en TallERP Telemetry

Esta implementación se basa en `docs/GT02.pdf`, versión 1.3 del documento del
fabricante. GT02 comparte el listener TCP `:8899`, el decoder, el spool SQLite y
el worker de entrega con GT06.

## Formato de frame y CRC

- `78 78`: longitud de paquete de un byte.
- `79 79`: longitud de paquete de dos bytes, big-endian.
- La longitud incluye protocolo, contenido, serial y CRC; no incluye cabecera,
  el propio campo de longitud ni `0D 0A`.
- El CRC-ITU se calcula desde el primer byte de longitud hasta el serial
  inclusive, con valor inicial `0xFFFF`, polinomio reflejado `0x8408` y
  complemento final.
- El serial ocupa dos bytes big-endian y el frame termina en `0D 0A`.

El decoder tolera frames fragmentados o concatenados, descarta ruido anterior a
una cabecera y valida longitud, CRC y stop bits antes del parser.

## Detección y sesión

El header no identifica la familia. Un login GT02 `0x01` contiene 12 bytes:
IMEI BCD (8), tipo de dispositivo (2) y zona horaria/idioma (2); el login GT06
existente contiene 8 bytes. Los mensajes exclusivos también pueden fijar GT02,
pero no se persiste ningún evento hasta disponer de IMEI.

El heartbeat `0x13` previo al login es ambiguo y recibe su ACK común sin ser
persistido. Después de tres frames ambiguos se permite todavía el ACK del cuarto
y se cierra la conexión. Una familia ya fijada nunca se redetecta silenciosamente.

## Mensajes implementados

| Dirección | Protocolo | Comportamiento |
| --- | --- | --- |
| Terminal → servidor | `0x01` | Login, IMEI/tipo/zona/idioma; ACK `0x01` inmediato |
| Terminal → servidor | `0x31` | GPS/LBS UTC, ACC y reporte histórico; sin ACK |
| Terminal → servidor | `0x13` | Estado, batería/voltaje y GSM; ACK `0x13` inmediato |
| Terminal → servidor | `0x32` | Alarma GPS/LBS/estado; ACK inmediato `0x26` |
| Terminal → servidor | `0x34` | LBS multibase; evento técnico durable |
| Terminal → servidor | `0x33` | Celdas y hasta cinco AP WiFi; evento técnico durable |
| Terminal → servidor | `0x94` | Información general; `0x0A` decodifica IMEI/IMSI/ICCID; sin ACK en esta versión |
| Terminal → servidor | `0x21` | Respuesta de comando ASCII o UTF-16BE (`79 79`) |
| Servidor → terminal | `0x80` | Constructor de comandos disponible; no existe ejecución automática |

Las fechas del tracker se interpretan como UTC. Las coordenadas son minutos
decimales multiplicados por 30000, equivalentes a dividir el entero por
1.800.000 para obtener grados. Los signos y heading provienen exclusivamente de
los bits GT02 del campo heading/status.

`0x31` conserva `gps_at` y `received_at` separados. El último byte de contenido
indica `is_retransmission`: `00` tiempo real y `01` transmisión suplementaria.
Una retransmisión binariamente idéntica genera el mismo `event_id`.

## Comandos

`BuildGT02Command` construye un frame `0x80` con server flag, comando ASCII,
idioma, serial y CRC. El comando debe ser ASCII imprimible y terminar en `#`.
No se envían comandos automáticamente. El manual documenta, entre otros:

```text
STATUS#
VERSION#
PARAM#
RESET#
SOS,...#
SERVER,0,IP,port,0#
SERVER,1,domain,port,0#
POWERALM,...#
BATALM,...#
MOVING,...#
RELAY,...#
```

Para apuntar manualmente un dispositivo a TallERP por dominio:

```text
SERVER,1,telemetry.tallerp.com,8899,0#
```

Esta operación debe realizarse fuera del servicio y validarse con el hardware.

## Seguridad y limitaciones

- IMSI e ICCID viajan solamente por la API interna. No se escriben completos en
  logs ni deben exponerse al frontend.
- No se geolocalizan observaciones LBS/WiFi y no se llaman servicios externos.
- No se implementan todavía `0x8D`, consulta de dirección `0x2A`, SMS, relay,
  UI/endpoints de comandos ni cambio automático de servidor.
- El formato combinado de idioma/extensión para voltaje externo y variantes de
  longitud indicadas de forma inconsistente por el manual requieren validación
  final con muestras OBD reales.
