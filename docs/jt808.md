# Protocolo JT808 en TallERP Telemetry

Esta implementación se basa en `JT 808 communication protocol technical
specifications V1.0`, el manual entregado por el fabricante de los OBD2.
JT808 comparte el listener TCP `:8899`, el spool SQLite y el worker de
entrega con GT06 y GT02, pero usa su propio framing, checksum y despachador
(`internal/protocol/jt808`), porque su formato de trama es incompatible con
el decoder compartido de GT06/GT02.

## Formato de frame, escape y checksum

- Cada mensaje va delimitado por `0x7E` al inicio y al final.
- Escape (aplicado a header+body+checksum, nunca a los delimitadores):
  `0x7E` → `0x7D 0x02`, `0x7D` → `0x7D 0x01`.
- El checksum es un XOR byte a byte desde el inicio del header hasta el
  byte inmediatamente anterior al propio checksum, calculado sobre los
  bytes ya sin escapar.
- `internal/protocol/jt808/decoder.go` tolera frames fragmentados o
  concatenados en una misma lectura TCP, y soporta tanto terminales que
  comparten un único `0x7E` entre mensajes consecutivos como los que envían
  dos delimitadores adyacentes.

## Header

```
Message ID                 WORD    offset 0
Message body properties    WORD    offset 2  (bits 0-9 longitud, 10-12 cifrado, 13 subpaquete)
Terminal SN                BCD[6]  offset 4  (identidad del dispositivo)
Message serial number      WORD    offset 10
Total packets / packet #   WORD+WORD  offset 12  (solo si el bit de subpaquete está activo)
```

El **Terminal SN** del header (no un campo del body) es el identificador
del dispositivo. **No es el mismo espacio de identificadores que el IMEI de
GT06/GT02.** Para reutilizar el pipeline existente (persistencia, contrato
de ingestión de Laravel), el servidor copia el Terminal SN al slot `IMEI`
de `TelemetryEvent`/`ConnectionContext` en cuanto se conoce (tras
registro o autenticación). Esto es una simplificación deliberada,
documentada como pendiente de validación con hardware real: cuando lleguen
los OBD2 físicos hay que confirmar si Terminal SN, IMEI e ICCID deben
mapearse a un único tracker de TallERP o si se necesita una tabla de
mapeo explícita.

Cifrado: el manual indica bits 10-12 en 0 (sin cifrar) para este firmware.
Si llega un mensaje con esos bits distintos de 0, se registra como no
soportado y se descarta el body — nunca se intenta descifrar.

## Detección y sesión

JT808 se detecta por el primer byte de la conexión: `0x7E` inicia JT808,
`0x78`/`0x79` GT06/GT02. La familia se fija una sola vez, igual que ya
ocurre entre GT06 y GT02, y nunca se re-detecta a mitad de conexión.

El terminal no debe enviar otros mensajes antes de autenticarse
exitosamente. El servidor exige registro (`0x0100`) o autenticación
(`0x0102`) antes de aceptar cualquier otro mensaje, con una excepción
deliberada: el heartbeat (`0x0002`) se permite también antes de
autenticar, porque hay firmware real que lo envía antes de completar el
flujo. Cualquier otro mensaje pre-autenticación recibe un `0x8001` con
resultado de fallo, sin cerrar la conexión.

## Mensajes implementados

| Dirección | Mensaje | Comportamiento |
| --- | --- | --- |
| Terminal → servidor | `0x0002` heartbeat | Body vacío; ACK `0x8001` inmediato, sin esperar spool ni Laravel |
| Terminal → servidor | `0x0100` registro | Genera/recupera un auth code persistente por Terminal SN; responde `0x8100` |
| Terminal → servidor | `0x0102` autenticación | Valida el auth code contra el store; responde `0x8001` |
| Terminal → servidor | `0x0200` ubicación | Ver detalle abajo; responde `0x8001` |
| Terminal → servidor | `0x0001` respuesta general | Solo se parsea (nada en este código envía comandos de plataforma automáticamente todavía) |
| Terminal → servidor | `0x0104` respuesta de parámetros | Solo se parsea/registra |
| Terminal → servidor | `0x0107` propiedades del terminal | Solo se parsea/registra |
| Servidor → terminal | `0x8103` set parámetros | Constructor disponible; nunca se invoca automáticamente |
| Servidor → terminal | `0x8104` query parámetros | Constructor disponible; nunca se invoca automáticamente |
| Servidor → terminal | `0x8105` control de terminal | Constructor disponible (incluye oil/electricity cutoff); **nunca se invoca automáticamente** |
| Servidor → terminal | `0x8107` query propiedades | Constructor disponible; nunca se invoca automáticamente |

Cualquier `Message ID` no reconocido se registra (`jt808_unsupported_message`,
métrica `UnknownMessageIDsJT808`), se responde con `0x8001` resultado
"not supported", y la conexión nunca se cierra por esto.

## Registro y autenticación

- `internal/jt808store` persiste `{terminal_sn, auth_code, manufacturer,
  model, registered_at, updated_at}` en una tabla nueva (`jt808_terminals`)
  dentro del **mismo archivo SQLite** que ya abre el spool
  (`internal/spool`), reutilizando la conexión ya abierta en vez de un
  segundo `sql.Open` contra el mismo archivo.
- El auth code es estable: un re-registro del mismo Terminal SN (por
  ejemplo tras un reset de firmware) recupera el mismo código en vez de
  generar uno nuevo, para no invalidar la autenticación ya guardada en el
  dispositivo.
- El auth code sobrevive reinicios del servicio.

## Reporte de ubicación (`0x0200`)

Parte fija (28 bytes) + lista variable de ítems TLV adicionales.

- **Coordenadas**: `latitud/longitud = valor crudo / 1.000.000`. El signo
  viene de `terminal status`: bit 2 = hemisferio sur, bit 3 = hemisferio
  oeste.
- **Velocidad**: `speed_kmh = crudo / 10.0`.
- **Dirección**: 0-359, 0 = norte verdadero.
- **Hora**: BCD `YY-MM-DD-hh-mm-ss`. El manual documenta GMT+8 doméstico /
  GMT en el extranjero como comportamiento por defecto del firmware, salvo
  configuración por SMS. **Para los dispositivos destinados a Venezuela no
  se asume GMT+8**: el servidor interpreta el campo como UTC directamente.
  Esto queda pendiente de validar contra el firmware real quel cuando
  lleguen los OBD2 físicos.
- **Terminal status**: se normalizan `acc` (bit 0), `gps_located` (bit 1) y
  `external_power` (bit 22) a los campos ya existentes de `TelemetryEvent`.
- **Alarmas**: JT808 no tiene un mensaje de alarma dedicado — las alarmas
  son flags dentro de `0x0200`, y un mismo reporte puede traer varias a la
  vez. Por eso se usa un campo nuevo `AlarmTypes []string` (en vez de
  reutilizar el `AlarmType *string` de GT06/GT02, que asume una sola
  alarma por evento). El `EventType` del evento se mantiene `"location"`;
  el log del servidor sí se emite en nivel `Warn` cuando hay alarmas
  presentes.

## Ítems adicionales (TLV)

`ID BYTE, longitud BYTE, valor` — un ID desconocido nunca rompe el parseo
del resto del mensaje; se conserva en `Raw` para diagnóstico.

| ID | Campo | Notas |
| --- | --- | --- |
| `0x01` | `device_mileage_km` | **Kilometraje calculado por el propio tracker, NO el odómetro del ECU.** Nunca sobrescribe el kilometraje estimado por GPS de TallERP; se compara por separado durante las pruebas con hardware real. |
| `0x02` | `fuel_volume_l` | 1/10 L |
| `0x10` | `battery_percent` | |
| `0x30` | `gsm_signal` | Valor crudo del manual, no se convierte a porcentaje |
| `0x31` | `satellites` | |
| `0x51` | `temperature_c` | 0.1 °C |
| `0x52` | `humidity_percent` | 0.1 % |
| `0x53` | celdas 2G | Se mapean a `Cells` (reutiliza el struct compartido con GT02) |
| `0x54` | WiFi | Se mapea a `WiFiAccessPoints` |
| `0x55` | celdas 4G | También mapea a `Cells` |
| `0xFE` | `external_voltage` | 0.1 V; en dispositivo cableado es el voltaje de alimentación externa, en inalámbrico es el voltaje de batería — el manual no distingue el tipo de dispositivo en el propio campo, así que esta ambigüedad queda pendiente de validar con hardware real |
| `0xE6` | `oil_percent` | |
| `0x56`, `0x57` | reconocidos pero no mapeados a dominio todavía | Se conservan en `Raw` |

## Subpaquetes

`internal/protocol/jt808/reassembly.go` reensambla mensajes divididos en
varios paquetes físicos (bit de subpaquete del header), tolerando llegada
fuera de orden y paquetes duplicados (el más reciente gana). Los buffers
incompletos expiran tras `DefaultReassemblyTTL` (2 minutos) para no crecer
indefinidamente si un terminal nunca termina de enviar un mensaje.

## Retransmisión y orden

El manual indica que el terminal guarda los reportes de ubicación cuando
la conexión es anormal y los reenvía al reconectar. El `EventID` se calcula
igual que para GT06/GT02 (`IMEI|Protocol|Serial|GPSAt|RawHex`, más un
sufijo `"jt808"` para no colisionar entre familias), así que una
retransmisión con el mismo serial, hora GPS y body produce el mismo
`EventID` — el spool la trata como duplicado sin necesidad de lógica
adicional.

## Modo diagnóstico

`TALLERP_JT808_DEBUG=true` habilita logs adicionales por frame: hex crudo,
hex sin escapar, Message ID, Terminal SN, longitud de body, ítems
adicionales parseados y hex de la respuesta. Desactivado por defecto.

## Métricas

`FramesReceivedJT808, RegistrationJT808, AuthSuccessJT808,
AuthFailureJT808, HeartbeatsJT808, LocationsJT808, ChecksumErrorsJT808,
ParseErrorsJT808, UnknownMessageIDsJT808`, además de sumar a los
contadores compartidos (`FramesReceived`, `LocationsReceived`,
`HeartbeatsReceived`) igual que ya hacen GT06 y GT02.

## No implementado en esta fase

- Subida de multimedia (`0x0800`/`0x0801`/`0x8800`): no aplica a
  telemetría OBD2/GPS.
- Entrega de mensajes de texto (`0x8300`/`0x0701`).
- Ejecución de comandos de control de terminal desde TallERP: `0x8105`
  existe solo como constructor (incluye apagado, reset, reset de fábrica y
  corte/restauración de combustible/electricidad), nunca se invoca
  automáticamente — igual que el precedente ya existente de `0x80` en
  GT02.
- Cuerpos de mensaje cifrados: se detectan y descartan con log, no se
  implementa descifrado.
- Subida de datos CAN bus (`0x0705`).

## Checklist de validación cuando lleguen los OBD2 físicos

1. Conectar el OBD2 apuntando a `telemetry.tallerp.com:8899`.
2. Observar en los logs `0x0100` (registro) o `0x0102` (autenticación).
3. Confirmar el Terminal SN reportado.
4. Verificar que la autenticación completa correctamente.
5. Confirmar heartbeat periódico (cada 3 minutos según el manual).
6. Confirmar recepción de `0x0200`.
7. Comparar coordenadas contra una referencia conocida.
8. Comparar velocidad reportada.
9. Validar el valor de señal GSM (`0x30`) contra la señal real del SIM.
10. Validar el número de satélites (`0x31`).
11. Comparar `device_mileage_km` (`0x01`) contra:
    - el odómetro del tablero del vehículo,
    - el kilometraje estimado por GPS de TallERP.
12. Apagar cobertura y forzar reconexión; confirmar que las retransmisiones
    no rompen el orden ni duplican eventos.
13. Confirmar la interpretación de hora (UTC vs. GMT+8) contra la hora real
    del reporte.
14. Confirmar si el voltaje (`0xFE`) corresponde a alimentación externa o a
    batería, según el tipo real de dispositivo.
